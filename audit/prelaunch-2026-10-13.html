CoopVote Launch Audit

Two reproduced critical defects block release: source and signing material can be downloaded through Git, and an election-deletion race can erase an acknowledged vote.

This report records the current state, including failures that the existing test suite missed. It is an audit, not a security certification or a claim that every possible defect has been found.

Keep the current build off public hosting. Close both critical findings first, then the high-severity security and ballot-integrity findings. Resolve privacy and election-policy decisions with the cooperative before approving a launch.

What was actually exercised

Completed technical checks

  • 13 baseline suites: 1,625 passed, 0 failed, 1 skipped. The skip was the legacy filesystem-upload execution probe because uploads/ids is absent.
  • 16 JavaScript test files passed. Backup cryptography: 27 checks passed. Encryption/TLS deployment checks: 8 passed.
  • 44 supplemental API observations: anonymous and voter/admin permissions, private endpoints, input types, withdrawn candidates, password sessions and cross-origin authentication.
  • 20 authenticated page/view types at 1440, 768, 390 and 360 pixels: 80 measurements plus two login observations. No authenticated-page uncaught errors, failed requests or page-width overflow were observed in these cases.
  • Three admin dialogs checked at 360 pixels. Rendered screenshots inspected for ballot, election form and officer management. Local navigation links resolved; a missing automatic favicon request is listed separately.
  • Simulated 1,500 ms latency and 400 kbps download, offline errors, HTTP 500, a 12-second stalled vote and response loss after commit.

Verified protections and boundaries

  • Sampled admin API routes rejected anonymous access with 401 and voter access with 403. Voter private endpoints rejected anonymous requests.
  • Baseline checks passed for SQL injection samples, escaped rendering checks, profile-image validation, required/blank form data, election approvals and election/position relationships.
  • Cross-election candidate/position assignment was rejected by a database foreign key independently of API validation.
  • Duplicate vote submission accepted exactly one attempt in the baseline race. A retry after a lost success response returned ALREADY_VOTED; the receipt remained recoverable.
  • Live database: 25 encrypted InnoDB tables, a 256-bit encryption key and verified TLS 1.3. HTTP redirects to HTTPS. TLS 1.0/1.1 rejected; TLS 1.2/1.3 accepted in the local check.
  • Published-result eligibility and private receipt checks passed the existing integration/regression suite. Identity-separated vote rows are not a formal proof of anonymity against a privileged database observer.

CriticalC01 Git repository exposes configuration and signing material over HTTP+

Observed evidence

Unauthenticated HTTPS GETs to .git/HEAD, .git/index and .git/config returned 200. Two Git objects returned 200 and were byte-for-byte identical to the tracked config/config.php and config/integrity-key.php objects. The tracked configuration contains a non-placeholder SMTP password; the other tracked file contains the vote integrity key. Direct /config requests correctly return 403, but the Git-object path bypasses that protection. No secret value is included in this report.

Impact and conditions

Someone who can reach this installation can recover tracked source and secret material. SMTP credential validity was not tested against Gmail. Possession of the signing key defeats key separation if the attacker also gains database-write access; it does not by itself grant database access.

Required change

Block the entire .git path at the server, deploy only an explicit runtime file allowlist, move secrets outside source and web roots, revoke/reissue the SMTP credential, and remove secrets from tracked files and history. Rotate the integrity key through a controlled migration that preserves existing signatures and reports; do not simply replace it and break verification.

Close-out test

Unauthenticated requests to Git files and objects must fail. A repository/history scan must find no real secrets. Old SMTP credentials must be revoked. Existing signed election records must still verify after the approved key migration.

CriticalC02 Deleting an election can erase a ballot that just received a success receipt+

Observed evidence

In an isolated two-request race, the first ballot returned HTTP 201 with a receipt and DELETE elections/{id} returned HTTP 200 with deleted=true. Afterwards both the election and its votes had zero remaining rows. The deletion handler checks the vote count before deleting without holding the same election-row lock as vote submission.

Impact and conditions

A legitimate administrator deleting an apparently empty election at the same moment as its first vote can erase an acknowledged ballot through cascading foreign keys.

Required change

Make deletion and its checks one transaction using the same election lock as voting. Recheck ballot/vote counts after acquiring the lock. Disallow destructive deletion of open or used elections; use a controlled cancellation/archive workflow and review cascading-delete constraints.

Close-out test

Repeat the controlled first-vote/delete race. Either deletion is refused and the successful vote remains, or deletion wins and voting is refused without a receipt. Never return success for a ballot later deleted by the competing request.

HighH01 Voting accepts a withdrawn candidate+

Observed evidence

Set a candidate to is_active=0 in the isolated fixture, then submit that candidate ID. The API returned 201 and stored a vote. Candidate listing and ballot rendering filter inactive candidates, but the submission validator collects all candidates returned by vt_candidates().

Impact and conditions

A stale ballot or direct API request can count a vote for a candidate who is no longer eligible to receive votes.

Required change

Validate active candidate status inside the voting transaction after taking the election lock. Serialize candidate changes using the same lock and revalidate each chosen candidate and position.

Close-out test

Inactive-candidate requests must return a clear 4xx response and leave both vote rows and has_voted unchanged, including concurrent withdrawal/submission.

HighH02 Malformed candidate IDs silently become real selections+

Observed evidence

Submitting candidateId as a nonempty array ["unexpected"] returned 201 in the test election. The direct integer cast converts a nonempty array to 1, which matched a real candidate in the fixture.

Impact and conditions

Malformed or corrupted input can record a candidate the request did not actually identify. Server-side validation must protect ballot meaning independently of keyboard restrictions.

Required change

Require strictly typed positive integer election and candidate IDs, validate each vote entry as an object/array with the expected shape, and reject booleans, arrays, objects, floats and malformed numeric strings before casting.

Close-out test

A type matrix must return 422 for malformed IDs and must not consume the ballot or add selections.

HighH03 Concurrent password failures bypass the intended lockout counter+

Observed evidence

Twelve simultaneous invalid-password requests across four PHP workers returned 401, but the account recorded only three failed attempts, zero lockouts and no locked_until value. The implementation reads the counter and later writes a computed value without serialization.

Impact and conditions

Parallel guessing substantially weakens the five-failure lockout. Known and unknown accounts also produce different failure messages, which permits account enumeration.

Required change

Use atomic counters/transactions for rate limiting, enforce account and source-based limits, and normalize externally visible failure messages while preserving internal diagnostics. Consider administrator MFA as an additional control.

Close-out test

Repeated concurrent failure bursts must trigger the documented limit reliably. Valid users must recover according to policy without an attacker being able to reset the counter through races.

HighH04 Changing a password leaves other authenticated sessions usable+

Observed evidence

Two independent clients signed in as the same voter. Client A changed the password successfully; the old password no longer logged in, but client B's existing session still fetched the private profile with HTTP 200. The password handler only updates password_hash.

Impact and conditions

Changing a compromised password does not remove an attacker who already has a session. The same password-change route accepts administrators.

Required change

Version or centrally track sessions, revoke other sessions on password change/reset, rotate the current session identifier and enforce idle/absolute expiry. Define a deliberate recovery policy for administrators.

Close-out test

A second pre-change session must lose access immediately after the change. The retained current session, if policy allows it, must use a new identifier.

HighH05 The application connects as the database superuser+

Observed evidence

The current application connection reports root@localhost. SHOW GRANTS includes ALL PRIVILEGES ON *.* WITH GRANT OPTION. config/config.php configures an empty database password. TLS and table encryption are enabled but do not reduce these account privileges.

Impact and conditions

An application compromise could affect other databases on the server and database accounts, not just CoopVote. No remote database access was assumed or tested.

Required change

Provision a dedicated password-protected runtime database user restricted to CoopVote and required operations. Separate migration/backup credentials. Review the metadata privileges needed by the encryption guard and keep the database network private.

Close-out test

The runtime user must be unable to access unrelated schemas, grant privileges or change accounts; all permitted application flows and encryption checks must still function.

HighH06 The local runtime is not a suitable production patch baseline+

Observed evidence

Current versions are Apache 2.4.58, PHP 8.2.12 and MariaDB 10.4.32. MariaDB documents 10.4 maintenance ending in June 2024. Official Apache and PHP release histories contain subsequent security fixes. PHP 8.2 as a branch is still supported until December 31, 2026; that does not make this old patch release current.

Impact and conditions

Deploying this exact XAMPP stack carries obsolete/unpatched components. Exploitability of each Apache/PHP advisory depends on the deployed modules and configuration and was not demonstrated here.

Required change

Select maintained, fully patched production components and perform compatibility, encryption, restore and workload tests on the actual hosting environment. Use a valid production-domain certificate and configured proxy trust.

Close-out test

Record installed versions, support dates and relevant security advisories at deployment; run the same acceptance/security suite against the production-equivalent stack.

HighH07 Activity logs are not tamper-evident+

Observed evidence

audit_logs has no chained-hash/signature fields, and audit() inserts ordinary mutable rows while swallowing failures. Changing an audit description directly in the isolated database produced HTTP 200 from the security endpoint, with the changed description displayed and no tamper warning. Vote HMAC protection is a separate mechanism.

Impact and conditions

A database writer can alter activity history without the claimed tamper-evident audit protection detecting it. This does not imply an ordinary voter can edit audit rows through the API.

Required change

If tamper-evident auditing is required, implement authenticated chaining with protected independent checkpoints or an external append-only audit service, verification and actionable alerts. Define fail-safe handling for important events and do not claim protection retroactively for an unverified baseline.

Close-out test

Altering, inserting, deleting, reordering and truncating audit entries must be detected against an independently retained checkpoint.

MediumM02 Voting has incomplete stalled-request and failure recovery+

Observed evidence

A held vote request remained in a disabled Submitting state after 12 seconds; the shared api() has no request deadline and the confirmation cannot be closed while submitting. A forced ballot API 500 displayed No Active Election. When the server returned 201 but its response was lost, the UI told the voter to check the connection and retry without first reconciling ballot state. A subsequent retry correctly returned ALREADY_VOTED and the receipt endpoint recovered the receipt.

Impact and conditions

On unreliable internet, voters can be trapped waiting or misled about whether an election exists or whether their vote counted. The tested duplicate protection held; no duplicate ballot was produced.

Required change

Use bounded request deadlines with explicit pending/error states. After an ambiguous vote result, check authenticated ballot/receipt status before offering a retry. Keep true empty states separate from failed requests and expose an accessible retry action.

Close-out test

Test a stalled request, offline-before-send, response loss after commit, HTTP 500, recovery and session expiry. A timeout must never be presented as proof that no vote was recorded.

MediumM03 Authentication lacks consistent CSRF and method protection+

Observed evidence

A form-encoded login POST with an untrusted Origin header was accepted with HTTP 200. GET auth/logout was also accepted. Some newer modules require JSON/custom headers, but authentication does not. SameSite=Lax provides protection for many existing-session cross-site POSTs; it does not solve login CSRF or state-changing GETs.

Impact and conditions

A crafted login form can establish an unwanted account session, and cross-site top-level navigation can force a logout. The audit did not claim arbitrary cross-site administrative writes bypass SameSite protections.

Required change

Apply a consistent CSRF policy to state-changing endpoints, validate Origin where appropriate, require POST for logout and use tokens or equivalent protections for login and multipart flows.

Close-out test

Simple cross-origin forms and navigations must not change session/account state; legitimate same-origin clients must keep working.

MediumM05 Membership eligibility is not independently enforced at vote time+

Observed evidence

In a deliberately inconsistent fixture with users.status=active but members.membership_status=inactive, vote submission returned 201. Normal admin deactivation updates both fields, so the observed bypass requires inconsistent data from import, manual changes or a future failure path.

Impact and conditions

If membership status is an eligibility condition, account status alone is not a sufficient server-side guarantee. Turnout eligibility counts likewise read active user status rather than membership status.

Required change

Confirm the cooperative's eligibility policy and enforce it in one shared transactional guard used for counts, ballots and vote submission. Prevent contradictory account/member states where possible.

Close-out test

Test all account/membership status combinations, missing member records, import paths and status changes during a pending vote.

MediumM07 Ballot abstention rules disagree between browser and API+

Observed evidence

The browser labels contested positions Required, disables Submit until all have a selection and returns early from openConfirm for incomplete ballots. The API accepts any nonempty set of valid positions, and the baseline UAT-07 test explicitly approves skipping a seat.

Impact and conditions

The rule enforced depends on the client. This is a policy inconsistency, not evidence that abstention itself should be forbidden.

Required change

Choose the cooperative's abstention rule, then align UI copy, validation, API behavior and acceptance tests. If abstention is allowed, make it an explicit understandable choice.

Close-out test

Normal browser users and direct API clients must receive the same rule for partial ballots and empty ballots.

Coverage that still needs completion

Deployment and security

  • The actual host, domain certificate, reverse-proxy settings, database network/firewall, least-privilege accounts, backups and monitoring have not been verified on a production-equivalent installation.
  • Current tests use seeded users and email disabled. Real account-delivery mail, bounce/retry handling and mail load need a controlled staging test.
  • No externally independent penetration test, exhaustive fuzzing, DDoS test or complete third-party dependency CVE assessment was completed.
  • Secret rotation and repository-history cleanup require verification; deleting a current file is not enough.
  • Ballot storage separates identity from choice rows but does not prevent all timing/order inference by a privileged observer. Formal anonymity requires a separately defined threat model.

People, devices and policy

  • Chrome viewport emulation is not a physical Android/iPhone test. Safari, Firefox, real touch keyboards, screen readers and all six themes require targeted acceptance checks.
  • Only three dialogs received additional narrow-screen checks; not every dialog, content-length extreme or assistive-technology path was visually inspected.
  • Human UAT and a supervised mock election still need cooperative participants and recorded sign-off. Automated suites named UAT/Pilot do not substitute for those steps.
  • Privacy policies, data retention, DPO responsibilities, incident response and access rules for member photos require organizational review.
  • Resolve the abstention rule and confirm the intended electorate, publication process, ties, cancellation/reopening and operator recovery procedures.

Data protection during the audit

Before rebuilding the scratch database, an AES-256-GCM backup of coopvote_test was created and restore-verified. After all destructive probes, the original test database was restored: all 25 table row counts matched, including 19 users, 18 members, 5 elections and 6 votes. The live coopvote database was not rebuilt, cleared or used for mutation probes; live checks were limited to read-only metadata and unauthenticated HTTP inspection.
